# ODIR + GenLayer: the whole system, in one essay

Written 31 October 2026 for a reader (human or model) who needs the complete picture before touching any part. Everything marked "today" was read from the local checkout `<ODIR_REPO>` (the private checkout) at commit 57b33b1 on branch `odir/harness-repairs`, the Base44 Mission Control app, and the contract source `contracts/odir_review_gate.py` (sha256 f27688d0…de5341). Everything marked "target" is design, not a claim that it exists.

## 1. What the system is for, and the one rule that shapes it

ODIR (the Orchestration Director) takes a human objective, turns it into a bounded run contract, dispatches model agents to build inside that contract, verifies the result, and decides what the next permitted action is. GenLayer adds a second, independent, consensus-backed semantic review of the evidence: several validators each ask a model whether the submitted text satisfies each acceptance criterion, and the contract only advances if their criterion statuses agree exactly. Base44 (Mission Control) is the window the owner looks through and the place they press buttons.

The single rule that shapes every tier is: evidence supports a decision; authority comes only from local policy plus the required human disposition. A convincing explanation, a green dashboard badge, a finalised blockchain transaction, or a signed report are each inputs. None of them is permission. The builder (the agent that writes code) must never custody the thing that limits it: not the permit signing key, not the test attestation key, not the exporter, not the wallet. When you read any component below, ask "what does this prove, and who is allowed to turn that proof into an action?" If the answer is "the same process that produced the proof", the design is wrong.

Three evidence levels stay visible everywhere: what the owner supplied (documents, the D1 demo transcript), what was independently inspected (a file read, a test observed by a trusted collector), and what was demonstrated on the actual host under its real operating-system boundary. Today almost all security controls are at the first two levels. The Windows adapters for principals, ACLs, the elevated approval tool, key custody and the event log are stubs that throw `HostUnverifiedError`; Gate 4 of the host plan is blocked; 29 reviewer findings are open. The 24 earlier contract tests were local stand-ins, not GenVM runs. This is not a defect of the design; it is the honest state of a prototype, and every tier below says what has to become true before it may claim more.

## 2. The components and how work flows through them

There are four repositories or places of code. Orchestrator-Swarm is the private swarm: Director, Operator, Governor, security adapters, exporter, Base44 sync. GenLayer-Integration-ODIR (public, `github.com/thesharkfxandfutures-dev/GenLayer-Integration-ODIR`) holds the review contract, the shared JSON schemas, cross-runtime fixtures and the narrow adapter CLI `genlayer-odir`. The Base44 app holds Mission Control: the `director` backend function and the entities DirectorRun, PipelineNode, ControlRequest, DirectorHeartbeat, AgentLane and CloudDirector. The GenLayer Studionet contract at `0xFE76B46a8345Fd8e07A8aA092BA715c8a4C3C646` is the deployed review gate. ODIR_HOME (`<ODIR_HOME>`) is the local authority and evidence store: verdicts.jsonl, slice board, assurance reviews, config and the sync secret.

The flow is a loop with one external excursion. A human states an objective, through the CLI (`odir run`) or by pressing Start on a Mission Control card, which the standby Director picks up as a ControlRequest. ODIR fixes a run contract: objective, intent, repository, base revision, allowed paths and commands, eligible providers, budget, repair limits, which review categories are advisory or mandatory, and which human approvals are required. The Governor runs preflight against the canonical control matrix and decides which execution mode is open; where a permit is required it issues one bound to revision, mission hash and a one-hour expiry. The Director schedules dependency-ready tasks to agent lanes (Claude CLI, Codex, Gemini, Antigravity) inside a disposable worktree, with the execution broker and containment adapters mediating file writes, subprocesses and egress. A verifier collects observed evidence: command, arguments, exit status, candidate digest, environment, start and finish time. The evidence bundle is HMAC-keyed and bound to the candidate hash.

Then the excursion. The exporter builds a review package: a candidate-bound JSON record naming the run, slice and attempt, the candidate manifest digest, the run-contract hash and policy version, the criteria with their evidence class, the exact inline evidence text and its digest, provenance and assurance level, the export-manifest digest and release approval, the destination chain, contract address and contract code identity, a lifetime and an idempotency key. Only the approved readable text leaves the machine. The adapter submits it to the contract; the builder wallet calls `submit_evidence`, the reviewer wallet calls `review_submission`, validators evaluate independently and compare criterion statuses, and the contract records REVIEWED_PASS, REJECTED or INSUFFICIENT. A separate reviewer action `approve_submission` binds a specific attempt and evidence hash; an executor wallet may later `consume_approval` once. The adapter observes `get_slice`, validates the reply shape, checks chain, contract and code identity, and reconciles it against the local package: CONSISTENT, PENDING_REVIEW, NOT_SUBMITTED, SUPERSEDED, EXPIRED, CONFIG_MISMATCH or INTEGRITY_MISMATCH. That reconciliation is written locally and projected to Base44 as an additive observation. It carries `authority: none`.

Back inside, the Governor combines the remote finding with the unchanged candidate, the local verification, current identity status and the run contract. Where the review is advisory it is displayed, not required. Where it is mandatory, absence or ambiguity leaves authority unavailable. The required human disposition is specific: approve reviewed attempt 1, authorise the next slice, commit, push, deploy. A permit for one narrow action is issued and rechecked by the broker at the operation boundary, where it confirms worktree unchanged, action in scope, not expired, not revoked, not consumed. Failed or unavailable required checks leave the permit unavailable. Repair creates a new candidate and a new attempt with lineage, never a silent carry-forward of a previous approval.

Everything crosses boundaries as JSON. Director to Base44 is a signed POST, HMAC-SHA256 over timestamp and body with a five-minute window, sequence-numbered against replay, with the reply signed back. Exporter to contract is the inline evidence string and criteria array; the contract recomputes `criteria_sha256` and `evidence_sha256` using Python's `json.dumps(sort_keys=True, separators=(',',':'), ensure_ascii=True)`, and the adapter's `canon.js` reproduces that encoding byte for byte so hashes agree across Python, Node and the Base44 function. Contract to adapter is the `get_slice` string. Adapter to Governor is the observation and reconciliation records. Every record names its schema and version, carries its own digest, states its assurance level and states that it is not authority.

## 3. The three tiers: what each one is, and what must change to reach it

The three product opportunities are three answers to one question: where do authority and evidence live, and who can prove that? Each tier keeps everything from the one below and moves one class of thing out of the local user's hands.

**Tier one, the developer tool: one person, one machine, local files, Base44 as a mirror, the CLI as the only hands.** This is what exists. The architecture does not change; the packaging does. Make the review package and observation schemas the only objects that cross a process boundary, and give every file `schema`, `sha256`, `assurance`, `authority` and an empty `signatures` array from day one so that later tiers add fields instead of changing formats. Extend `odir init` with a `genlayer` block (network label, chain id, RPC URL, contract address, contract code sha256, adapter path) and add an `odir review` command that shells out to `genlayer-odir`, preserving the zero-dependency rule. Keep an append-only local log of observations and reconciliations beside verdicts.jsonl and project it to a new, additive Base44 entity with observed_at, freshness and integrity fields; do not repurpose DirectorRun.verification_outcome or any existing role or flag, and do not change the HMAC wire format. Approval history is a read model derived from those records, never a status someone set. The adapter stays read-only: no key, no submission, RPC reads fail closed as BLOCKED_ENVIRONMENT until the calldata encoding and a pinned client are verified against the real runtime. Valuable because setup is one command, findings arrive with quotes and reasons, and the approval history is complete and honest. Its limit, stated on every page: one Windows account holds the builder, the keys, the evidence and the permit file, so nothing here is enforcement, only tamper evidence and cooperative discipline.

**Tier two, the team governance product: several people, enforced permissions, private evidence, reliable recovery.** This is the first real architectural shift and it is the same work as the frozen security phase. Authority leaves the home directory and moves behind the Gate running as its own principal: run contracts, permits, verdicts, the review outbox and inbox become a service the CLI, Director and Operator are clients of, not owners of. The single shared HMAC secret, which only proves "someone holding the secret", is replaced for authority purposes by per-role asymmetric keys: owner, builder, verifier, exporter, submitter, executor. The package's `signatures` array fills with who signed which digest under which key id, and Mission Control shows it. Evidence becomes private by default: the exporter applies a classification (public, internal, confidential, secret), field and file allowlists, bounded excerpts, secret scanning and human release approval for new templates; the package splits into a public review part and a private evidence archive linked by digest, with the sanitised digest never described as the raw one, and a confidential review route exists for source that cannot be public. Delivery stops being "a file on disk" and becomes an outbox with a persisted request key before any broadcast and an inbox with uniqueness constraints on package and transaction ids, so a lost response, a duplicate notification or a crash between the chain write and the local write is reconciled, not retried blindly. Base44 grows from one admin role to tenancy: row-level security per organisation, per-run read scopes, approval cards that name the exact disposition and the exact wallet or principal, and tests that one tenant cannot read another's evidence or manufacture an approval. The mandatory gate becomes possible here, for one low-risk category at a time, only after acceptance and denial are demonstrated on every dispatch route including the separate Operator and direct adapters; any route that cannot enforce the permit is disabled for that category. Valuable because permissions are enforced by a different principal than the one doing the work, evidence stays inside the organisation's policy, and a crash or a revocation leaves a consistent state. Its limit: a trusted elevated administrator remains outside the boundary, and OS-level containment of arbitrary worker processes is still cooperative plus tamper-evident unless tier three is reached.

**Tier three, the enterprise security platform: independently tested containment, identity integration, support and operational assurance.** The design changes least here; the assurance claims change most, and that drives packaging and operations. The H2 to H13 stubs become real Windows (or other platform) adapters: separate standard-user principals with no interactive logon, ACLs applied from a validated plan so the runtime cannot write authority paths, an audit ledger only the audit principal can append to with an independent replica and owner-held anchors, a Security-log observer that detects omission on a real induced gap, an elevated owner approval tool whose key a non-elevated token cannot use, Job Objects or AppContainer for worker processes, gate-owned leases, scheduled tasks registered only by the owner, and credentials under gate-only ACL or DPAPI. Each is demonstrated on the target host by a party other than the builder, with an attempted bypass per protected operation, and a control stays HOST-UNVERIFIED until then regardless of what the source contains. Identity integrates with the enterprise: OS or identity-provider principals replace local key files, and the package's signatures reference key ids or certificates the enterprise can audit and revoke. The monolithic source tree remains, but packaging produces separate runtime bundles for Gate, audit, observer, exporter, adapter and runtime, each with its own principal, credentials, route allowlist, logs and retention. Operations become a product: budgets on package size, criteria count, attempts, consensus rotations and transaction spend; measured review latency with alerts; pinned runner, SDK and contract code identities with an upgrade policy that says whether older verdicts remain valid; monitoring of unavailable collectors, failed exports, invalid signatures, consensus format errors, stale approvals and repeated denials; an incident procedure that first stops new authority issuance, preserves evidence, reconciles completed operations and rotates credentials through an authorised process; retention set separately for raw evidence, sanitised packages, authority decisions and dashboard caches, remembering that an on-chain copy cannot be deleted. The release dossier records requirement coverage, test results on the real runtime, known limitations, independent review outcomes and a signed activation approval. Valuable because a customer can be shown, not told, where an unauthorised write, command, request or deployment is refused. Its limit is the one every such platform has: correlated model error, adversarial evidence and policy decisions remain human responsibilities, and the dossier must say so.

## 4. How to read the state of the system at any moment

Ask five questions and insist on five separate answers. What does the local execution record say (RUNNING, SUCCEEDED, FAILED)? What does local verification say (VERIFIED, UNPROVEN, FAILED, STALE, NOT_RUN, decided from records, never by a button)? What does the remote review say (PASS, FAIL, INSUFFICIENT_EVIDENCE, or pending, with chain, contract, code identity, observation time and freshness)? What human disposition exists (none, approve reviewed attempt, accept unverified, authorise next slice, commit, push, deploy)? What permit exists (none, issued for which action, expiry, consumed, revoked)? An execution SUCCESS is not a semantic PASS; a FINALIZED transaction may contain an execution error; an APPROVED attempt is not a completed external action; a CONSUMED approval is spent even though its review still reads PASS; a mismatched hash or invalid signature is an integrity event to investigate, not an outage to retry.

The build order follows the dependency order in the requirements baseline, R01 through R12: inventory the real checkout and every dispatch route; fix the run contract and roles; mediate execution; bind candidates to evidence; control export; define the versioned package; complete the contract lifecycle and its GenVM denial tests; make the adapter durable; let the Governor decide; make recovery and revocation real; project it honestly; then assure and publish. The developer tier is complete when R06 to R08 and R11 work in advisory and read-only mode against the real contract. The team tier is complete when R02, R03, R05, R09 and R10 are demonstrated on every route and one mandatory category passes acceptance and denial. The enterprise tier is complete when the host items are independently verified and the release dossier is signed. At every increment, publish the assurance level actually achieved, because the credibility of the whole system rests on never letting a readable design, a verified runtime observation, an accepted policy and a technically enforced permission be mistaken for one another.
